# QANOW 질의응답 게시판 Constitution

## Core Principles

### I. 회원-관리자 권한 분리 (Role Separation)
회원(Member)과 관리자(Admin)의 권한 범위를 스펙 단계에서 명시적으로 정의하고, 두 역할이
수행 가능한 행동(조회, 작성, 수정, 삭제, 상태 변경 등)의 목록이 겹치지 않게 문서화한다.
UI, API, 데이터 접근 계층 어디에서도 역할이 불명확한 상태로 기능을 노출하지 않는다.

**이유**: 질의응답 게시판은 회원 개인정보와 게시글 소유권이 얽혀 있어, 권한 경계가
모호하면 정보 노출·무단 수정 사고로 직결된다. 권한을 먼저 정의해야 이후 검증(원칙 II)과
UI 설계가 흔들리지 않는다.

**검토 기준**: 각 기능 명세에 "이 행동을 누가 할 수 있는가"가 회원/관리자로 명시되어
있는가? 두 역할의 권한표가 스펙 문서에 존재하는가?

### II. 데이터 계층 최종 강제 (Server-Side Authorization)
권한 검사는 UI에서 버튼을 숨기거나 비활성화하는 것으로 끝나지 않는다. 모든 쓰기/조회
요청은 서버(API 또는 데이터 접근 계층)에서 요청자의 역할과 소유권을 재확인한 뒤 처리한다.
클라이언트 측 검사는 UX 편의를 위한 보조 수단일 뿐, 유일한 방어선이 되어서는 안 된다.

**이유**: UI 검사는 우회가 가능하다(직접 API 호출, 개발자 도구 등). 실제 보안 경계는
서버와 데이터 계층에만 있다.

**검토 기준**: 코드 리뷰 시 "이 UI 제한을 우회해 API를 직접 호출하면 서버가 거부하는가?"를
확인한다. 거부하지 못하는 쓰기/조회 경로는 병합할 수 없다.

### III. 사용자 입력 검증 (Input Validation)
게시글, 댓글, 회원 정보 등 사용자가 입력하는 모든 값은 서버 측에서 형식·길이·필수값을
검증한 뒤 저장한다. 클라이언트 검증은 선택이지만 서버 검증은 필수다.

**이유**: 검증되지 않은 입력은 데이터 무결성 훼손, XSS 등 보안 취약점, 예기치 않은
런타임 오류의 원인이 된다.

**검토 기준**: 각 입력 필드에 대해 서버 측 검증 로직과 실패 시 사용자에게 반환되는
오류 메시지가 존재하는가? 빈 값/과도한 길이/비정상 타입 입력에 대한 테스트가 있는가?

### IV. 명세 범위 준수 (No Unscoped Features)
현재 스펙(spec.md)에 명시되지 않은 기능, 화면, 버튼, 옵션을 구현 중 임의로 추가하지
않는다. 필요하다고 판단되면 먼저 스펙을 갱신하거나 별도 이슈로 제안한다.

**이유**: 임의 기능 추가는 범위를 통제 불능으로 키우고, 권한 분리(원칙 I)나 MVP
단순성(원칙 XI)과 충돌할 위험을 검증되지 않은 채로 만든다.

**검토 기준**: PR/Task의 변경 사항이 spec.md의 요구사항으로 역추적되는가(원칙 XII와
연결)? 추적 불가능한 UI 요소나 엔드포인트가 있는가?

### V. 핵심 화면 정보구조·디자인 일관성 (Cross-Screen Consistency)
세 핵심 화면(예: 목록, 상세, 작성/수정)은 동일한 내비게이션 위치, 용어, 컴포넌트
스타일(버튼, 카드, 폼)을 공유한다. 화면마다 임의로 다른 레이아웃 패턴을 도입하지 않는다.

**이유**: 일관성이 깨지면 사용자가 화면마다 새로 학습해야 하고, 유지보수 시 스타일
분기가 누적된다.

**검토 기준**: 세 화면의 헤더/버튼/상태표시 컴포넌트가 동일한 디자인 토큰·컴포넌트를
재사용하는가? 신규 화면 추가 시 기존 패턴과의 차이를 설명할 수 있는가?

### VI. 시각 효과의 성능·가독성 우선 (Visual Effects Must Not Cost Usability)
메인 페이지의 그래픽 효과(애니메이션, 그라디언트, 파티클 등)는 콘텐츠 가독성과 초기
로딩/렌더링 성능을 저해하지 않는 범위에서만 허용한다. 효과가 핵심 정보(질문 제목,
상태, CTA)를 가리거나 지연시키면 제거하거나 축소한다.

**이유**: 질의응답 게시판의 본질은 정보 탐색이며, 장식적 효과가 그 목적을 방해하면
안 된다.

**검토 기준**: 주요 콘텐츠가 첫 화면에서 즉시 식별 가능한가? 효과 적용 전후 로딩
체감 성능에 뚜렷한 저하가 없는가?

### VII. 모션 접근성 (Reduced Motion Support)
모든 애니메이션/트랜지션은 `prefers-reduced-motion` 미디어 쿼리를 확인하고, 해당
설정이 켜진 사용자에게는 애니메이션을 생략하거나 즉시 상태로 대체한다.

**이유**: 전정 장애 등으로 모션에 민감한 사용자를 배려하는 것은 접근성의 기본 요건이다.

**검토 기준**: 새로 추가되는 CSS/JS 애니메이션마다 `prefers-reduced-motion: reduce`
분기가 존재하는가?

### VIII. 키보드 접근성 (Keyboard-Operable Core Actions)
질문 작성, 답변 작성, 검색, 로그인 등 주요 행동은 마우스 없이 키보드만으로 완료할 수
있어야 한다. 포커스 순서가 논리적이며, 포커스 표시가 시각적으로 확인 가능해야 한다.

**이유**: 키보드 사용자와 스크린리더 사용자의 접근을 보장하는 것은 최소한의 웹 접근성
요건이다.

**검토 기준**: Tab만으로 주요 행동 흐름을 완료할 수 있는가? 포커스 인디케이터가
제거되지 않았는가?

### IX. 색상 단독 의존 금지 (Status via Color + Text)
답변 채택 여부, 게시글 상태(공개/비공개, 처리중/완료 등)는 색상만으로 구분하지 않고
텍스트 라벨이나 아이콘+텍스트 조합으로 함께 표시한다.

**이유**: 색각 이상 사용자나 흑백 환경에서도 상태를 구분할 수 있어야 한다.

**검토 기준**: 색상을 제거해도(그레이스케일로 봐도) 상태를 구분할 수 있는가?

### X. 데스크톱·모바일 핵심 시나리오 완결성 (Cross-Device Completion)
핵심 사용자 시나리오(질문 등록, 답변 작성, 검색·조회)는 데스크톱과 모바일 뷰포트
양쪽에서 처음부터 끝까지 완료 가능해야 한다. 한쪽에서만 동작하는 필수 기능을 남기지
않는다.

**이유**: 사용자층이 데스크톱과 모바일에 걸쳐 있으므로, 한쪽에서 시나리오가 막히면
서비스 이용 자체가 불가능해진다.

**검토 기준**: 핵심 시나리오별로 데스크톱/모바일 각각에서 수동 또는 자동 테스트로
완료를 확인했는가?

### XI. 단순한 MVP 구조 우선 (MVP Simplicity)
기능은 가장 단순하게 동작하는 구조로 먼저 구현하고, 추상화·설정·확장 포인트는 실제
필요가 확인된 뒤에만 추가한다. 사용되지 않는 유연성을 미리 설계하지 않는다.

**이유**: 초기 단계에서 과도한 설계는 검증되지 않은 가정 위에 복잡성을 쌓아 유지보수
비용만 키운다.

**검토 기준**: 새 인터페이스/설정/추상화 계층이 현재 요구사항에 의해 실제로 필요한가,
아니면 미래를 위한 추측인가?

### XII. Task의 요구사항·디자인 추적성 (Traceable Tasks)
모든 구현 Task는 어떤 요구사항(spec.md의 항목)과 어떤 디자인 근거(plan.md, 디자인
문서)에서 비롯되었는지 명시한다. 근거 없이 생성된 Task는 존재할 수 없다.

**이유**: 추적성이 없으면 왜 이 코드가 존재하는지 알 수 없고, 명세 범위 준수(원칙 IV)를
검증할 방법이 사라진다.

**검토 기준**: tasks.md의 각 항목에 관련 요구사항 ID/디자인 문서 참조가 기재되어
있는가?

### XIII. 테스트·빌드 실패 시 미완료 처리 (Green Build Gate)
테스트 또는 빌드가 실패한 상태의 작업은 완료(Done)로 표시하지 않는다. 실패를 해결하지
못하면 진행 중 또는 차단(Blocked) 상태로 유지한다.

**이유**: 실패 상태를 완료로 처리하면 이후 작업이 깨진 기반 위에 쌓이고, 문제 발견이
지연된다.

**검토 기준**: Task/PR을 완료 처리하기 전 CI(테스트+빌드)가 녹색인가?

## Accessibility & Responsive Standards

원칙 VI~X(시각 효과, 모션, 키보드, 색상, 반응형)는 WCAG 2.2 AA 수준을 최소 기준으로
삼는다. 신규 UI 컴포넌트를 추가할 때는 이 다섯 원칙을 체크리스트로 순회한 뒤 병합한다.

## Development Workflow & Quality Gates

- 모든 PR은 원칙 I~IV(권한, 검증, 명세 준수)를 위반하지 않는지 리뷰어가 확인한다.
- 접근성 관련 변경(V~X)은 실제 키보드 조작과 `prefers-reduced-motion` 켠 상태에서
  최소 1회 수동 확인을 거친다.
- Task 생성 시 원칙 XII에 따라 요구사항/디자인 근거를 기재하지 않으면 리뷰를 통과할
  수 없다.
- 원칙 XIII에 따라 테스트/빌드가 실패한 PR은 병합하지 않는다.

## Governance

본 헌법은 QANOW 프로젝트의 다른 모든 관행(코딩 컨벤션, 개별 PR 판단 등)보다 우선한다.
원칙과 충돌하는 결정은 헌법을 먼저 개정한 뒤에만 유효하다.

**개정 절차**: 원칙 추가/삭제/재정의는 변경 사유와 영향 범위를 기록한 뒤 이 문서를
갱신하고 Sync Impact Report를 최상단에 남긴다.

**버전 정책**: MAJOR - 기존 원칙의 삭제 또는 양립 불가능한 재정의, MINOR - 원칙/섹션
신규 추가 또는 실질적 확장, PATCH - 표현 수정·오탈자·비의미적 다듬기.

**준수 검토**: 모든 PR/코드리뷰는 위 Development Workflow & Quality Gates 항목을
근거로 원칙 준수 여부를 확인한다. 복잡성이 추가될 경우 원칙 XI(MVP 단순성)에 비추어
정당화되어야 한다.
